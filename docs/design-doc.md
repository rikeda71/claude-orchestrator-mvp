# マルチClaude ワークフローシステム設計書

## 1. 概要

### 1.1 背景
Anthropicのエンジニアリングベストプラクティス記事「Claude Code Best Practices」の第6章「Uplevel with multi-Claude workflows」に基づき、複数のClaude Codeインスタンスを協調させて動作するシステムを構築します。

### 1.2 目的
- 複数のClaude Codeインスタンスによる並列開発の実現
- 役割分担による効率的なタスク処理
- 自動的なコードレビューとドキュメント管理
- コンテキストウィンドウの効率的な管理

### 1.3 システム構成
本システムは5つのtmuxセッションで構成され、それぞれが特定の役割を持つClaude Codeインスタンスを実行します：

1. **プロジェクトマネージャー (PjM)** - 1セッション
2. **エンジニア（実装者）** - 2セッション（eng1, eng2）
3. **レビュワー** - 1セッション
4. **Design Docライター** - 1セッション

## 2. アーキテクチャ

### 2.1 ディレクトリ構成
```
claude-orchestrator/
├── sessions/          # 各セッション用ディレクトリ
│   ├── pjm/          # プロジェクトマネージャー
│   ├── eng1/         # エンジニア1
│   ├── eng2/         # エンジニア2
│   ├── reviewer/     # コードレビュワー
│   └── docs/         # ドキュメントライター
├── tasks/            # タスク管理
│   ├── queue/        # 待機中のタスク
│   ├── in-progress/  # 進行中のタスク
│   ├── completed/    # 完了したタスク
│   └── reviews/      # レビュー待ちタスク
├── worktrees/        # Gitワークツリー
│   ├── main/         # メインブランチ
│   ├── eng1/         # エンジニア1の作業領域
│   └── eng2/         # エンジニア2の作業領域
├── communication/    # セッション間通信
│   ├── pipes/        # 名前付きパイプ（FIFO）
│   ├── buffers/      # 共有バッファ
│   └── logs/         # セッションログ
├── scripts/          # オーケストレーションスクリプト
└── docs/            # ドキュメント
```

### 2.2 通信アーキテクチャ

#### 2.2.1 タスク管理システム
- **形式**: JSON形式のファイルベース
- **状態遷移**: pending → in-progress → review → completed
- **保存場所**: `tasks/`ディレクトリ配下

#### 2.2.2 セッション間通信
1. **名前付きパイプ（FIFO）**
   - リアルタイム通信用
   - 双方向通信チャネル
   - `/tmp/claude-pipe-*`に配置

2. **tmuxバッファ共有**
   - セッション出力のキャプチャ
   - `capture-pane`コマンドによる取得
   - 他セッションへの転送

3. **ファイルシステム**
   - タスクキューの共有
   - ログファイルによる監査証跡
   - 状態の永続化

### 2.3 Git ワークフロー
```
メインリポジトリ
    ├── worktree: eng1-feature (エンジニア1用)
    └── worktree: eng2-feature (エンジニア2用)
```

- 各エンジニアは独立したworktreeで作業
- コンフリクトの回避
- レビュー後のマージ自動化

## 3. 各役割の詳細

### 3.1 プロジェクトマネージャー（PjM）

#### 責務
1. タスクの作成と割り当て
2. 進捗の監視と報告
3. 依存関係の管理
4. コンテキスト使用量の監視
5. 必要に応じた`/clear`コマンドの実行

#### 主要機能
- タスクキュー（`tasks/queue/`）の管理
- エンジニアへのタスク割り当て
- 完了タスクの確認と報告
- システム全体のヘルスチェック

### 3.2 エンジニア（実装者）

#### 責務
1. 割り当てられたタスクの実装
2. 専用worktreeでの作業
3. 進捗状況の更新
4. レビュー依頼の送信

#### ワークフロー
1. タスクキューから自身のタスクを確認
2. タスクを「進行中」にマーク
3. 専用worktreeで実装
4. 完了後、レビュー依頼を送信
5. フィードバックに基づく修正
6. 承認後、PjMに完了報告

### 3.3 レビュワー

#### 責務
1. コードレビューの実施
2. 複数実装者のコード整合性確認
3. フィードバックの提供
4. マージ承認

#### レビュープロセス
1. レビュー依頼の受信
2. 差分の確認（`git diff`）
3. コードの品質チェック
4. フィードバックまたは承認
5. マージ可否の判断

### 3.4 Design Docライター

#### 責務
1. Google Design Doc形式での設計文書作成
2. 実装に基づくドキュメント更新
3. エンジニアへの仕様確認
4. 設計の一貫性維持

#### 活動パターン
- 能動的：新機能の設計文書作成
- 受動的：実装変更に基づく更新
- 協調的：エンジニアへの低頻度問い合わせ

## 4. タスク管理

### 4.1 タスク構造（JSON形式）
```json
{
    "id": "task-001",
    "type": "feature|bug|review|docs",
    "assigned_to": "eng1|eng2|reviewer|docs",
    "status": "pending|in-progress|review|completed",
    "description": "タスクの説明",
    "created_by": "pjm",
    "created_at": "2024-11-02T10:00:00Z",
    "dependencies": ["task-000"],
    "worktree": "eng1-feature",
    "files": ["src/module.py"],
    "review_notes": []
}
```

### 4.2 タスクライフサイクル
1. **作成**: PjMがタスクを作成し、キューに配置
2. **割り当て**: 適切なエンジニアに割り当て
3. **開始**: エンジニアがタスクを開始、ステータスを更新
4. **レビュー**: 実装完了後、レビュー依頼
5. **修正**: フィードバックに基づく改善
6. **完了**: 承認後、マージして完了

## 5. 監視とメンテナンス

### 5.1 コンテキスト管理

#### 監視項目
- コンテキスト使用率（95%で警告）
- 自動圧縮の検出
- メモリ使用量
- トークン使用量の推定

#### 対応アクション
1. 使用率95%超過時：PjMに通知
2. `/clear`コマンドの実行
3. セッション役割の再初期化
4. 作業継続性の確保

## 6. 実装スクリプト

### 6.1 主要スクリプト一覧

| スクリプト名 | 用途 | 説明 |
|------------|------|------|
| `claude-orchestrator.sh` | メイン制御 | システム全体の起動と管理 |
| `claude-task.sh` | タスク管理 | タスクのCRUD操作 |
| `claude-monitor.sh` | 監視 | コンテキスト使用量の監視 |
| `claude-review.sh` | レビュー管理 | レビューワークフロー |
| `claude-messenger.sh` | 通信 | セッション間メッセージング |
| `start-system.sh` | 起動 | システム起動シーケンス |
| `stop-system.sh` | 停止 | グレースフルシャットダウン |

### 6.2 起動手順
```bash
# 1. システムの起動
./start-system.sh

# 2. タスクの作成（PjM経由）
./claude-task.sh create feature "ユーザー認証の実装" eng1

# 3. レビュー依頼
./claude-review.sh request task-001 eng1 feature/eng1-20241102

# 4. システムの停止
./stop-system.sh
```

### 9.2 トラブルシューティング

#### よくある問題と対処法
| 問題 | 症状 | 対処法 |
|------|------|--------|
| セッション応答なし | コマンドが実行されない | セッション再起動、`/clear`実行 |
| タスク重複 | 同じタスクが複数回実行 | タスクIDの確認、キューのクリーンアップ |
| Git競合 | マージコンフリクト | worktreeの再作成、手動解決 |
| 通信エラー | メッセージが届かない | パイプの再作成、権限確認 |

## 10. まとめ

本設計書で定義したマルチClaude ワークフローシステムは、複数のAIエージェントを協調させることで、従来の単一エージェントでは実現困難だった並列開発と品質管理を可能にします。

### 主な利点
- **並列処理**: 複数タスクの同時実行
- **役割分離**: 専門性に基づく効率的な作業分担
- **品質保証**: 自動レビューによる品質維持
- **スケーラビリティ**: 必要に応じた拡張が容易

### 成功要因
1. 明確な役割定義と責任分担
2. 効率的な通信メカニズム
3. 自動化されたワークフロー
4. 継続的な監視とメンテナンス

本システムの実装により、大規模なソフトウェア開発プロジェクトにおいても、AIアシスタントを効果的に活用した開発が可能となります。
